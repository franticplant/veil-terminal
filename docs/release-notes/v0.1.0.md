# Veil Terminal v0.1.0

First stable VM-first release.

## What's in this release

- **VM-first engine.** The normal path runs the Rust SSH engine inside a
  protected Microdroid VM. The native process engine remains explicitly
  selectable and is never substituted silently after a VM failure.
- **Separate VM host.** `io.github.franticplant.veil.vm` owns the AVF
  permissions and starts the fixed payload. It has no `INTERNET` permission
  and never receives SSH private keys.
- **Keystore signing.** SSH keys stay in Android Keystore. New keys require
  strong-biometric authentication for each signing operation; device-PIN
  fallback is not used for signing. StrongBox is the default where available,
  with TEE available as an explicit compatibility choice.
- **Broker and worker processes.** The experimental Workers VM layout runs a
  supervisor, a separate broker process, a single-threaded spawner, and one
  short-lived worker process per session. Sessions use connection leases,
  validated frames, merged component logs, and bounded worker shutdown.
- **SSH bastions.** Profiles can use one optional jump host. The first TCP
  stream goes to the bastion; the worker opens a direct-tcpip channel and runs
  the final SSH transport through it.
- **Better terminal chrome.** Session tabs remain visible in terminal
  fullscreen, and the cover-notch path no longer leaves a blank top bar when
  tabs are disabled.
- **Diagnostics.** The VM host, broker, spawner, supervisor and workers report
  useful logs through the dev control plane.

## Important migration notes

- **Old SSH keys are refused.** Keys created before the auth-per-use policy
  are labelled `legacy key`; recreate and re-authorize them.
- **StrongBox / TEE.** New keys default to StrongBox on devices that advertise
  it. TEE remains usable as an explicit compatibility choice.
- **Locked-down signing.** Each signature requires a strong-biometric prompt.
  The secure hardware authorizes the signing operation, not a displayed
  hostname; the app still validates the SSH key, user, host and session.
- **Workers is experimental.** The default VM layout is Monolith. Workers can
  be selected in Settings; Tenants is not part of this release and fails
  explicitly.
- **Bastion limitation.** v0.1.0 supports one bastion using the target's
  username and selected key. Per-hop identities, multiple hops and forwarding
  are follow-up work.

## Install

1. Install the main Veil APK.
2. Install the `.vm` APK.
3. Grant the one-time AVF permissions:

   ```sh
   scripts/grant-avf
   ```

4. Open Veil → Settings → Engine → **VM (Microdroid)**, then restart Veil.

VM mode requires an AVF/Microdroid-capable device. This release was validated
on a Pixel 8 running GrapheneOS. Native mode needs only the main APK and
remains available as an explicit fallback.

## Caveats

- The default VM layout is Monolith. Workers is experimental; Tenants is not
  included in this release.
- The main app currently holds `INTERNET` and SSH signing authority. The
  planned `.net` and `.vault` package split is not part of this release.
- The VM package has no `INTERNET` permission and never receives private keys.
- Workers inside one VM still share UID 6000; they give process, data and crash
  separation, not a hostile multi-session authority boundary.
- Total memory use includes the app, VM host and guest; no combined memory
  guarantee is claimed yet.
- Native mode has weaker isolation than the protected VM.

## Verification

Every release file is signed with the pinned Veil key. Checksums and GitHub
attestations are attached to the release.

```sh
sha256sum -c SHA256SUMS
gh attestation verify <file> -R franticplant/veil-terminal
apksigner verify --print-certs <file>.apk
```

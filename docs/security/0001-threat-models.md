# Veil Terminal threat models: Workers now, Tenants target

Generated by OpenAI GPT-6.1 Sol (medium) from a review of the current tree,
2026-10-30. This is a security analysis, not a claim that every target control
exists.

## Scope and evidence

**Workers provides useful process containment, but not strong isolation between
mutually hostile sessions. Tenants would strengthen boundaries between roles,
not between sessions within the worker pool.**

This review distinguishes:

- **Implemented:** behavior visible in the reviewed source.
- **Observed:** device/probe results recorded in
  [design/0005](../design/0005-guest-decomposition.md) and supplied current
  facts; not independently rerun here.
- **Target:** proposed Tenants behavior, not implemented.
- **Unverified:** properties requiring additional tests or platform evidence.

Monolith remains the stable single-process payload. Workers is implemented,
experimental, and exercised with sequential and concurrent sessions. **Tenant
probe success is not implementation or end-to-end validation of the Tenants
engine layout.**

No code changes were made for this analysis.

## 1. Components, authority, and trust boundaries

### Current Workers layout

```text
 Android app package                         Android .vm package
 ┌────────────────────────────┐             ┌──────────────────────────┐
 │ UI / SessionRegistry       │  Binder +   │ Signature-protected       │
 │ host-key pins and policy   │  pipes/FDs  │ IVmHost service           │
 │ LoginSigner → Keystore     │◄───────────►│ AVF lifecycle authority   │
 │ NetBroker opens TCP        │             │ EngineProxy / TCP relay  │
 └────────────┬───────────────┘             │ No INTERNET, no keys     │
              │ TCP                         └────────────┬─────────────┘
              ▼                                         │ vsock
       Remote SSH server                     VM boundary│
                                                        ▼
 ┌──────────────────── Microdroid VM ─────────────────────────────────┐
 │ Supervisor process — UID/GID 6000                                 │
 │   engine listener :5000; session routing; worker-output gate       │
 │   passive endpoint/lease queues; ciphertext relay                 │
 │       │                                                          │
 │       ├── broker process — UID/GID 6000                           │
 │       │     vsock 5001; accepted streams via SCM_RIGHTS           │
 │       │                                                          │
 │       ├── pre-forked, single-threaded spawner — UID/GID 6000        │
 │       │      ├── single-use session worker A — UID/GID 6000        │
 │       │      └── single-use session worker B — UID/GID 6000        │
 │       │                                                          │
 │       └── per-worker control + data Unix socket endpoints         │
 │            delivered by spawner using SCM_RIGHTS                  │
 └───────────────────────────────────────────────────────────────────┘
```

The broker is now a **separate process**, but it still shares **UID/GID 6000**
with the supervisor. This gives code/memory and crash separation; it does not
yet give role-authority separation. A compromised broker can still signal the
supervisor, exhaust shared resources, or exploit a supervisor bug.

### Target Tenants layout — not implemented

```text
                                          ▼
 ┌──────────────────── Microdroid VM ─────────────────────────────────┐

 │          │     network ciphertext and stream assignment           │
 │          │                                                       │
 │          └── Worker-pool tenant ≈ UID 10002                       │
 │                 single-threaded spawner                           │
 │                   ├── session worker A, UID 10002                 │
 │                   └── session worker B, UID 10002                 │

 │ explicit session bindings, narrowly controlled SCM_RIGHTS         │
 └───────────────────────────────────────────────────────────────────┘
```

UIDs are illustrative allocations, not portable constants. Target role IPC has
not been implemented.

### Authority inventory

| Component | Data and authority |
|---|---|
| Android app | Owns the user interface, session/key selection, host-key policy, signing requests to Keystore, and network dialing. Sees terminal output and user input. It is trusted for session confidentiality and authorization. |
| Android Keystore | Holds SSH identity private-key material; non-exportability does not prevent an authorized compromised app from requesting signatures. |
| `.vm` host | Controls VM lifecycle and relays engine protocol and connected TCP FDs. Has AVF permissions but no `INTERNET` or SSH identity keys. **Its engine-protocol relay carries plaintext terminal/input/prompt data.** |
| Supervisor | Owns session routing and worker control channels. Sees user input, parsed terminal frames, prompts, and signatures returned through the bridge. Does not normally possess SSH transport keys or identity private keys. |
| Guest broker | Handles endpoint metadata, SSH negotiation bytes, and encrypted SSH traffic—not decrypted terminal traffic. It is a separate process in Workers, but still UID/GID 6000; Tenants is required for role authority separation. |
| Spawner | Creates and reaps session workers and transfers socket endpoints. Descriptor hygiene and fork safety make it security-critical. |
| Session worker | Owns one SSH transport, transport keys, terminal parser/state, session plaintext, and authentication responses. Gets a single-use stream through `FixedDialer`; no identity private key. |
| Guest kernel / AVF platform | Enforces process, UID, and VM boundaries. Shared-kernel compromise is outside the protection provided by tenant UIDs. |

**Important distinction:** the SSH identity private key stays on Android. SSH
transport/session keys necessarily exist inside the worker.

## 2. Threat models

### Model 1 — Compromised session worker

**Assets at risk:** the compromised session's plaintext, transport keys,
authentication responses, terminal integrity, signing authorization, and other
sessions' availability.

**Attacker capabilities and prerequisites:** arbitrary code execution in a
worker, for example through SSH/terminal parsing or a dependency vulnerability.
Assume the attacker can make syscalls and send arbitrary worker-control
messages.

**Entry points:** SSH packets, terminal bytes, worker IPC output, and the
worker's connected stream.

**Trust boundary crossed:** worker → supervisor/app authority; worker → sibling
processes.

**Attack paths**

- Read or modify its own session; send arbitrary traffic over its connected
  stream.
- Forge another session's frames or prompts.
- Generate valid-looking login-signing requests for its assigned session.
- Signal sibling workers, the supervisor, or the spawner under the shared UID.
- Exploit supervisor decoding or frame validation to escape containment.
- Seek inherited descriptors or readable shared files.

**Existing controls**

- Separate address spaces and FD tables; one single-use process per session.
- Spawner forks before listeners and supervisor runtime exist.
- Worker closes the spawner control descriptor and unused socket endpoints.
- `FixedDialer` consumes its stream once.
- Supervisor-side worker adapter checks session IDs and `check_frame`, and
  allowlists message types.
- Worker startup attempts `NoNewPrivs`, `Dumpable=0`, `RLIMIT_NOFILE=128`, and
  zero core dumps.
- No direct guest Internet; outbound vsock connection was observed denied.

**Residual risk**

- Compromise fully loses the worker's own session.
- Same-UID signals permit cross-session and whole-engine DoS.
- No seccomp prevents arbitrary syscall use or additional forks.
- `Dumpable=0` protects the **target process** from normal same-UID tracing; it
  is not a complete same-UID sandbox.
- Supervisor and worker hardening failures are warnings, not startup failures.
  Spawner dumpability is not explicitly hardened in the reviewed path.
- Login-request validation does not independently prove the requested SSH
  exchange belongs to an approved destination.

**Concrete mitigations**

- Verify required hardening before handling session data; fail closed for
  security-critical failures.
- Explicitly harden the spawner and audit every inherited descriptor.
- Bind signing grants to a live session, selected key/user, connection
  generation, expiration, and an explicit authorization policy.
- For independently verified destination-bound signing, establish a trusted
  binding to the SSH exchange; labels supplied by a compromised worker are
  insufficient.
- Use Tenants for role-level signal protection; use per-session credentials or
  VMs for session-level authority separation.

**Acceptance tests**

- From worker A, attempt cross-session frames, prompts, stats, signing requests,
  and unsupported message types; none may affect B.
- Attempt `ptrace`, `process_vm_readv/writev`, `/proc/<pid>/mem`, and FD access
  against every role.
- Enumerate inherited FDs before session start and after concurrent sessions
  exist.
- Inject worker crashes and signals; document the current same-UID DoS rather
  than expecting isolation that does not exist.
- Attempt a legitimate-format signing request for an unrelated SSH exchange;
  measure whether current policy signs it.

### Model 2 — Malicious SSH server or hostile terminal content

**Assets at risk:** worker execution integrity, terminal/UI availability,
clipboard integrity, credentials entered by the user, and user trust in
displayed content.

**Attacker capabilities and prerequisites:** controls an SSH server the user
reaches, or controls output produced through an otherwise trusted server. A
malicious authenticated server does not need to defeat SSH encryption.

**Entry points:** SSH negotiation/authentication messages, terminal escape
sequences, Unicode/text, titles, bells, and clipboard offers.

**Trust boundary crossed:** remote-controlled bytes → worker parsers → app
rendering and user actions.

**Attack paths**

- Exploit SSH or VT parsing.
- Trigger excessive allocations, parser work, rendering, bells, or prompts.
- Present deceptive shell output, authentication prompts, titles, or clipboard
  content.
- Exploit malformed frames after compromising the worker.

**Existing controls**

- SSH host-key decisions are app-owned.
- SSH and VT processing occur inside a session worker.
- Render frames are validated by the supervisor-side adapter and frontend.
- Frame contract bounds dimensions, cursor/run positions, text controls, and
  titles.
- Protocol messages have a 4 MiB encoded-size limit.
- Clipboard output is represented as a remote-controlled offer; frontend policy
  decides what reaches the clipboard.

**Residual risk**

- Host-key verification authenticates a server; it does not make that server
  benign.
- Structurally valid terminal text can still deceive users.
- `check_frame` does not validate every prompt, error, clipboard, or
  security-state field.
- An encoded-size bound is not a total decoded-memory or CPU budget.
- `check_frame` uses unchecked `u32` arithmetic such as `run.col + run.cells`;
  overflow cases need explicit testing.

**Concrete mitigations**

- Fuzz SSH/VT processing and all worker-originated message types.
- Use overflow-safe frame-bound checks.
- Apply semantic limits and rate limits to prompts, clipboard offers, errors,
  and bells.
- Keep app-owned connection identity and approval UI visually separate from
  remote terminal text.
- Require deliberate clipboard acceptance; do not execute or interpret offered
  content.

**Acceptance tests**

- Exercise malformed SSH, escape-sequence storms, huge combining sequences,
  prompt floods, and slow output.
- Test `u32::MAX` frame coordinates/counts in debug and release builds.
- Verify invalid frames cannot reach rendering and valid hostile text cannot
  impersonate app chrome.
- Confirm remote content cannot silently overwrite clipboard or trigger local
  execution.

### Model 3 — Compromised network broker or relay

**Assets at risk:** stream assignment, endpoint metadata, connection
availability, and—if authentication is subverted—session confidentiality.

**Attacker capabilities and prerequisites:** controls a relay component or can
supply its input. Distinguish an on-path network attacker from code execution in
the current guest broker.

**Entry points:** TCP relay, vsock 5001, endpoint header parsing, ready/waiting
queues, and stream handoff.

**Trust boundary crossed:** supplied network stream → assigned session.

**Attack paths**

- Replace, reorder, truncate, stall, or misroute streams.
- Stall the single guest accept thread with an incomplete endpoint header.
- Accumulate pending connections or endpoint entries.
- Swap streams for concurrent sessions to the same endpoint.
- Exploit guest broker code and gain supervisor-process authority today.

**Existing controls**

- Android opens TCP; `.vm` receives a connected FD.
- SSH cryptographic integrity and app-owned host-key policy protect against an
  ordinary malicious relay, assuming honest SSH workers.
- Endpoint header lines are length-bounded.
- Guest ready queues retain at most 16 streams **per endpoint**.
- Host relay cleanup closes both directions when either ends.

**Residual risk**

- The broker is a separate process but still shares UID/GID 6000 with the
  supervisor, so broker compromise is signal/resource DoS, not memory
  compromise; tenant separation is still required for authority.
- Connection leases now bind a stream to `(host, port, connection_id)`. The
  legacy zero-lease endpoint fallback remains for old clients.
- No header-read deadline is visible.
- Endpoint maps lack visible global cardinality limits.
- Guest outbound relay uses an unbounded channel.

**Concrete mitigations**

- **Implemented:** endpoint-only matching was replaced by a frontend connection
  lease carried through `OpenSession` and the broker header. The broker matches
  `(host, port, connection_id)`; the zero/legacy fallback remains.
- Add handshake deadlines, bounded global queues, canceled-waiter cleanup, and
  bounded outbound buffering.
- **Partially implemented:** broker is a separate same-UID process; move it to
  a tenant UID before claiming broker-compromise authority containment.
- Keep the broker outside host-key and signing authority.

**Acceptance tests**

- Open A/B to the same endpoint, reorder preparation/opening, cancel A, and
  reconnect; verify exact ownership.
- Send partial headers and flood distinct endpoints; unrelated sessions must
  progress within defined limits.
- Stall TCP writes and measure bounded relay memory.
- Inject ciphertext corruption; it must fail SSH, not silently alter plaintext.
- In the target, compromise the broker tenant and test denied access to
  supervisor memory/control sockets.

### Model 4 — Compromised supervisor

**Assets at risk:** every session's visible terminal output, user input,
authentication responses, routing integrity, and access to app-side signing.

**Attacker capabilities and prerequisites:** arbitrary execution in the
supervisor through protocol handling, worker-output parsing, or the currently
co-located broker.

**Entry points:** engine protocol, worker IPC, broker headers, session
lifecycle, and descriptor handling.

**Trust boundary crossed:** guest coordinator → Android policy/signing authority
and all session control planes.

**Attack paths**

- Read or change input and parsed output across all sessions.
- Route credentials or commands to the wrong session.
- Forge host-key prompts, sign requests, or security-state reports.
- Suppress failures or misrepresent a session's connection state.
- Stop all workers; currently also signal them directly.

**Existing controls**

- Identity private keys and canonical host-key policy remain Android-side.
- Android signer checks selected key, expected username, and SSH public-key
  authentication structure.
- Frontend validates frames and protocol sizes.
- Supervisor does not normally parse SSH or VT byte streams.

**Residual risk**

- The supervisor is an all-session confidentiality and integrity trust point.
- Tenants does not remove this protocol authority.
- App host-key policy relies on a guest-reported key; a compromised guest can
  lie about what it observed.
- SSH userauth structure checking prevents general-purpose signing, **not
  necessarily signing a login for an attacker-selected exchange**.
- Nonzero worker `request_id`s are forwarded unchanged for allowed messages;
  worker errors are forwarded without session scoping. The app uses nonzero IDs
  to complete pending requests.

**Concrete mitigations**

- Treat all guest claims as untrusted assertions, not independent proof of
  authentication.
- Restrict app-side signing by live session state, grant lifetime, prompt replay
  protection, and bounded concurrency.
- Normalize worker events to `request_id=0`; independently correlate only
  explicitly supported internal replies.
- Define typed, role-specific IPC rather than forwarding generic engine
  messages.
- Keep supervisor parsing and dependencies minimal.

**Acceptance tests**

- With a malicious supervisor harness, request wrong-key, wrong-user, malformed,
  replayed, expired, and unrelated-exchange signatures.
- Verify app pins cannot be silently changed through fabricated guest messages.
- Forge worker errors/events using another pending request ID; no unrelated
  request may complete.
- Verify a compromised supervisor cannot extract identity private-key material,
  while documenting its substantial permitted signing and session-control
  reach.

### Model 5 — Compromised Android app or `.vm` host

**Assets at risk:** all displayed/input session data, network destinations,
signing authority, VM configuration, and availability.

**Attacker capabilities and prerequisites:**

- **App compromise:** execution in the app that owns UI, network access, pins,
  and Keystore authorization.
- **`.vm` compromise:** execution in the package that owns AVF and relays
  protocol/FDs.
- An unrelated Android app has neither authority merely by being installed.

**Entry points:** frontend dependencies, Binder service, engine pipes, supplied
TCP FDs, lifecycle/configuration calls, and diagnostics.

**Trust boundary crossed:** Android package boundaries and host → VM control.

**Attack paths**

- Compromised app steals input/output, changes destinations/pins, and requests
  signatures.
- Compromised `.vm` reads or modifies the unencrypted engine-protocol relay and
  supplies fake guest messages.
- Authorized callers stop/restart the VM or request non-protected/debug
  configurations.
- A compromised same-signing-key companion abuses the signature-protected
  service.

**Existing controls**

- `.vm` is a separate Android package without `INTERNET` or keys.
- Service requires a signature-level permission.
- `IVmHost` selects fixed layouts, not arbitrary payload paths.
- VM backend does not silently fall back to native.
- Client Binder death triggers VM shutdown.
- Probe shell is build-gated.

**Residual risk**

- **VM isolation does not protect terminal plaintext from the app or `.vm`
  protocol relay.**
- No `INTERNET` does not revoke connected-socket authority received through
  Binder.
- Fixed payload selection restricts honest service behavior; it is not a
  guarantee against arbitrary execution inside `.vm`.
- Protected VM memory isolation does not authenticate an unencrypted
  application-protocol relay.
- Authorized callers can request protection/diagnostic settings; release policy
  must be explicit.

**Concrete mitigations**

- Enforce release constraints for protected mode, diagnostics, and permitted
  layouts at the service—not only UI.
- Audit all packages sharing the signing key and VM-host permission.
- Restrict operations to the active owner/session where appropriate; a signature
  permission is not per-client ownership.
- If a malicious `.vm` must be tolerated, design an authenticated guest channel
  and credible guest-identity verification. This does not solve a malicious
  UI/app.
- Minimize/redact diagnostic logs.

**Acceptance tests**

- An unrelated signed APK cannot bind/control the service.
- Release builds reject diagnostic-shell access and prohibited VM modes.
- Mutate protocol data inside `.vm`; document current exposure rather than
  expecting AVF to detect it.
- Kill app/host during startup and active sessions; verify cleanup.
- Check logs for terminal text, credentials, signatures, and sensitive endpoint
  metadata.

### Model 6 — Same-UID session DoS and resource exhaustion

**Assets at risk:** all-session availability, VM memory, CPU, threads, FDs,
process slots, and recoverability.

**Attacker capabilities and prerequisites:** malicious server induces heavy
work, or compromised worker directly consumes resources, forks, or sends
signals.

**Entry points:** output floods, session churn, worker syscalls, shared
supervisor queues, relay buffers, and spawner lifecycle.

**Trust boundary crossed:** one session's resource consumption → shared VM and
other sessions.

**Attack paths**

- `SIGKILL`/`SIGSTOP` supervisor, spawner, or siblings.
- Allocate until guest OOM, spin CPU, or fork repeatedly.
- Flood the shared output queue and starve other sessions.
- Stop reading worker control, hang shutdown, or leave descendants alive.
- Repeatedly close logically finished sessions while processes or relay threads
  remain.

**Existing controls**

- Maximum 16 tracked live sessions.
- Bounded protocol/command queues and normal-engine frame pacing.
- Worker `RLIMIT_NOFILE=128`; supervisor limit 256; core dumps disabled.
- Spawner periodically reaps exited children.
- Per-session processes contain ordinary crashes.

**Residual risk**

- **No worker `RLIMIT_AS` is currently applied:** `limits::apply(0, 128)` skips
  it.
- No demonstrated CPU/process-count limit or delegated cgroup enforcement.
- A tracked-session limit is not a bound on maliciously forked processes or hung
  workers.
- `RemoteWorker::close` requests shutdown; it does not provide a hard
  termination deadline.
- Worker-supplied stats are not trustworthy evidence against a compromised
  worker.
- Tenants leaves sibling workers and pool spawner at UID 10002. Pool-wide DoS
  remains.
- `memory.high` is not a hard memory limit and its enforcement is unmeasured.

**Concrete mitigations**

- Set measured per-worker address-space limits and aggregate admission budgets.
- Bound all relay buffers and schedule session output fairly.
- Add startup/shutdown deadlines and parent-owned worker identity/lifecycle
  tracking.
- Design handling for hung workers and descendants; recognize that same-UID
  workers can interfere.
- Measure tenant memory/CPU controls rather than infer isolation from
  configuration.
- Use per-session UIDs or separate VMs when malicious-session availability
  matters.

**Acceptance tests**

- Inject OOM pressure, CPU loops, forks, stopped workers/spawner, and unread
  control channels in a disposable test VM.
- Kill one worker and verify other sessions remain usable under ordinary crash
  conditions.
- Run extended connect/disconnect and simultaneous-session churn; track real
  process, thread, FD, and memory growth.
- Measure B's latency while A floods output.
- Set explicit pass thresholds for cleanup time and maximum resource
  consumption.

### Model 7 — Tenant role-boundary and IPC attacks

**Assets at risk:** supervisor authority, stream ownership, signing grants,
role-specific memory, and availability.

**Attacker capabilities and prerequisites:** compromise of a future broker or
worker-pool tenant; ability to connect to exposed Unix sockets and send hostile
messages/FDs.

**Entry points:** target Unix listeners, role handshake, SCM_RIGHTS, session
lifecycle messages, and tenant startup/restart.

**Trust boundary crossed:** tenant UID/role → another role's IPC authority.

**Attack paths**

- Impersonate a role or submit another session's identifier.
- Replay a stale request after a session or tenant restarts.
- Transfer listeners, files, pipes, duplicates, or excess FDs instead of
  expected stream endpoints.
- Exploit FD parsing/truncation/error cleanup.
- Use shared group permissions, `/proc` metadata, or SIGCONT behavior.
- Compromise the pool spawner and affect all future session workers.

**Existing controls / evidence**

- Probe tenants had distinct UIDs and zero effective capabilities.
- Cross-UID tested kill operations and ptrace were denied.
- SIGCONT was allowed in the same session; peer `/proc/status` was readable.
- Group 3009 remained; lab `NoNewPrivs=0`.
- **There is no implemented tenant-role IPC to credit with controls.**

**Residual risk**

- `SO_PEERCRED` authenticates credentials, not a logical session or permission
  to sign.
- Workers sharing a pool UID cannot be distinguished by UID alone.
- Manager-created tenants may retain shared group access and metadata exposure.
- The lab matrix does not prove denial for every signal, memory interface,
  filesystem path, or FD operation.

**Concrete mitigations**

- Define a role/message/FD authorization matrix before implementing IPC.
- Check expected peer credentials and bind a dedicated channel to one assigned
  session/generation.
- Validate FD count, type, intended use, ownership, and lifecycle; close all
  received FDs on rejection, including truncation paths.
- Use startup handshakes, generation-bound requests, deadlines, and explicit
  revocation.
- Set `NoNewPrivs`/`Dumpable=0` in production roles and verify effective
  capabilities.
- Reduce group exposure manager-side if possible; otherwise document and test
  it.

**Acceptance tests**

- Wrong-role, wrong-session, stale-generation, malformed, duplicate,
  unexpected-FD, and truncated-ancillary requests fail closed without leaks.
- Repeat the credential/signal/ptrace matrix on the actual engine roles and
  forked workers.
- Test peer memory/FD access separately from readable status metadata.
- Restart each tenant and verify old channels and grants cannot be reused.
- Verify a pool worker cannot request another session's authorization even
  though both share a UID.

### Model 8 — Supply chain, updates, and VM payload integrity

**Assets at risk:** all engine execution, identity-key usage, trusted policy,
and the credibility of isolation claims.

**Attacker capabilities and prerequisites:** malicious dependency/build input,
signing-key compromise, installation of an authorized malicious package,
rollback opportunity, or weakened VM configuration.

**Entry points:** APK/native payload updates, tenant package resolution, payload
configuration, signing authorities, and debug variants.

**Trust boundary crossed:** build/distribution authority → trusted runtime.

**Attack paths**

- Ship a malicious app, worker, supervisor, or tenant under an accepted signing
  identity.
- Enable diagnostic/debug behavior in release.
- Resolve a tenant package with the wrong signing authority.
- Introduce incompatible role versions or protocol downgrade behavior.
- Misrepresent "protected VM" as proof that the payload itself is trustworthy.

**Existing controls**

- Android package-signing infrastructure and fixed payload selection.
- Protected VM configuration is the default client setting.
- No silent native fallback.
- Probe documentation identifies `expected_authority` as SHA-512 of
  signing-certificate DER, not the SHA-256 fingerprint.
- Diagnostic shell is build-gated.

**Residual risk**

- A correctly signed malicious release remains malicious.
- Actual attestation, verifier policy, rollback resistance, and tenant-version
  compatibility are not established by these files.
- Optional reflection calls can fail silently; requested settings are not
  automatically evidence of effective settings.
- Tenant package identity verification must still be integrated into the target
  engine.

**Concrete mitigations**

- Protect release keys; review dependency changes and build provenance.
- Add release checks for debug/probe exclusion and effective VM configuration.
- Pin/validate tenant signing authorities and define compatible role-version
  sets.
- Verify AVF integrity and rollback properties against the deployment platform
  before claiming them.
- Use attestation only with a specified verifier, trusted reference identity,
  freshness, and channel binding.

**Acceptance tests**

- Wrong tenant certificate, missing package, incompatible version, missing
  layout, and unauthorized update all fail explicitly.
- Release artifacts contain no usable diagnostic shell.
- Verify protected/debug settings on the running VM.
- Exercise supported update/rollback paths and document observed enforcement.

## 3. Cross-session guarantees: now versus target

These guarantees assume an honest app/supervisor unless explicitly stated,
successful hardening, and no guest-kernel exploit.

| Property | Current Workers | Target Tenants |
|---|---|---|
| **Confidentiality** | Separate worker memory and FD tables reduce accidental disclosure. `Dumpable=0` is intended to prevent ordinary same-UID memory tracing. Session routing rejects foreign worker output. Not a complete hostile-session security boundary. App, `.vm` relay, and supervisor see session plaintext/control data. | Adds UID-enforced role memory/access restrictions, subject to platform/IPC validation. Worker-to-worker protection remains essentially the same process containment because sessions share UID 10002. Supervisor/app/host plaintext exposure remains. |
| **Integrity** | A worker's legitimate control channel is bound to its session; foreign-session frames/prompts are rejected. Own-session output can be forged. Shared coordinator and unchecked protocol-correlation details remain attack surfaces. | Role UID boundaries reduce direct role interference. Correct session/FD authorization still depends on new IPC. Does not make a malicious supervisor or worker truthful. |
| **Availability** | Ordinary worker crashes can be contained. A malicious worker can signal all same-UID roles and exhaust shared resources. | Most tested cross-role signals are denied; SIGCONT exception remains. Session workers can still signal siblings and pool spawner. Shared memory/CPU/kernel availability remains. |
| **Authority** | Normal worker gets one stream and no identity private key; uses app-mediated prompts/signing. Shared UID still grants signal authority. Session identifiers are routing checks, not independent kernel credentials. | Separates supervisor, broker, and pool authority by role. Does **not** give each session a separate UID, resource domain, or independently enforced signing identity. |

### What stronger session isolation requires

- **Per-session UIDs/tenants:** deny ordinary cross-session signals and
  credential-based access, with correctly configured groups, IPC, descriptors,
  dumpability, and resource controls. Fixed worker tenants may work; dynamic
  tenant creation is unverified.
- **Separate VMs per session/trust domain:** separate guest kernels and VM
  resource envelopes. This is stronger against guest-kernel compromise and
  whole-guest failure, at memory/boot cost.
- Neither approach alone isolates sessions from a shared malicious app, signer,
  or plaintext-routing supervisor. Those trust points require separate policy
  and, where needed, architectural changes.

## 4. Priorities

Here, **P0 means a blocker for the relevant security claim or release gate**,
not a claim that an exploit has been demonstrated.

### P0 — Resolve before making strong isolation or authorization claims

**Lifecycle note (2026-10-31):** the Workers supervisor now receives the
worker PID at handoff and holds a pidfd. A session close that has not exited
after two seconds escalates to `SIGKILL`. This bounds close; crash injection
and measured memory limits remain open.

1. **Do not market Workers or the proposed pool as hostile-session isolation.**
   Same-UID signal DoS is known.
2. **Define signing authorization under guest compromise.** Current checks
   constrain signature format/key/user, not independently verified
   destination/exchange authorization. New keys now require strong biometric
   auth per signing operation through Keystore; legacy keys are refused.
   Cooldown and OTC remain app policy, not hardware guarantees.
3. **Before enabling Tenants as a security feature, implement and adversarially
   test role/session/FD authorization.** Probe success alone is insufficient.
4. **Enforce the intended production VM/debug policy.** Do not publish dev-shell
   variants or describe debug/non-protected operation as equivalent protection.

### P1 — High-value engineering and acceptance work

- **Implemented:** endpoint FIFO matching was replaced by a frontend
  connection lease carried through `OpenSession` and the broker header. The
  broker matches `(host, port, connection_id)`; the zero/legacy fallback is
  retained only for native/legacy clients.
- Bound guest relay buffers, header timing, pending maps, and aggregate
  resources.
- Apply a measured worker memory limit; add deterministic shutdown/reaping
  tests.
- Verify hardening for supervisor, spawner, and workers; make critical failures
  actionable.
- Normalize worker event request IDs and scope errors.
- Harden frame arithmetic and fuzz every worker-originated message class.
- Run explicit crash, signal, FD-inheritance, long-lived leak, and
  malicious-worker tests.
- Verify actual tenant credential, group, `/proc`, signal, and resource
  behavior.

### P2 — Defense in depth and operational assurance

- Dependency/provenance review, version compatibility, and update/rollback
  testing.
- Diagnostic redaction and privacy-conscious metrics.
- Manager-side group reduction where available.
- Attestation only where a concrete external-verification requirement justifies
  it.
- Additional parser process splits only if measured benefits justify the cost;
  another same-UID process is not a new authority boundary.

## 5. Claims that must not be made

- "Tenants is implemented."
- "The current broker is isolated from the supervisor."
- "Each session has its own security identity."
- "A compromised worker cannot affect other sessions."
- "Workers have enforced per-session memory/CPU quotas."
- "Seccomp, Landlock, namespaces, or delegated cgroups sandbox current workers."
- "Cross-tenant signals are all blocked."
- "Different tenant UIDs hide peer `/proc` metadata."
- "The engine has no keys"—it has SSH transport keys, though not identity
  private keys.
- "No `INTERNET` means no network authority"—connected FDs confer authority.
- "Only safe cell frames cross the guest boundary"—prompts, signatures, states,
  errors, clipboard offers, and other messages also cross it.
- "Keystore prevents malicious login signing."
- "Protected VM means the app or `.vm` cannot see terminal data."
- "SO_PEERCRED proves session authorization."

## 6. Explain it to the user

1. **Workers is worthwhile:** each connection gets its own memory and parser
   process, so an ordinary crash is less likely to take everything down.
2. **It is not a wall between hostile sessions:** a hacked worker can currently
   stop other workers or the whole engine. Tenants would protect the major
   roles, but workers in the pool would still share this weakness.
3. **Your identity key stays in Android Keystore, but permission to use it still
   matters:** a compromised engine can ask for login signatures. Preventing key
   extraction is not the same as preventing unauthorized logins.
4. **The VM does not hide terminal data from the Android app or its VM host
   relay.** For genuinely separate trust domains, consider separate session
   credentials or VMs—and account for the shared app and signing policy too.
